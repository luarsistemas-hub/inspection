# ADR-005: Use Three Standalone Frontend Projects in One Repository

## Status

Accepted

## Date

2026-09-07

## Context

The current `apps/web` Next.js application combines tenant administration,
authenticated operational dashboards, and invitation-scoped capture. The PRD
requires independent products, URLs, sessions, releases, and layouts. The user
also chose dependency and lockfile isolation rather than a root JavaScript
workspace. Brand consistency must still be maintained across products.

## Decision

Replace `apps/web` with three standalone Next.js projects in the same monorepo:
`apps/admin`, `apps/dashboard`, and `apps/capture`. Each project owns its
`package.json`, `package-lock.json`, Dockerfile, build, tests, generated GraphQL
client, runtime configuration, and deployment pipeline. They are not members of
an npm workspace and must not import source files from one another.

Production uses `admin.<domain>`, `dashboard.<domain>`, and
`capture.<domain>`. Local development uses ports 3000, 3002, and 3003
respectively, preserving port 3001 for Gotenberg. Because the system has not
entered production, old `apps/web` URLs and previously issued capture links are
not preserved.

Shared visual primitives are published as a private, semantically versioned npm
package from `packages/inspection-design-system`. Each application pins an exact
package version and upgrades deliberately; local cross-package source imports
are forbidden.

## Alternatives Considered

### Alternative 1: One Next.js application with route groups

- **Description**: Keep Admin, Dashboard, and Capture as route groups in one deployment.
- **Pros**: Lowest build and dependency overhead; simplest local startup.
- **Cons**: Couples releases, sessions, middleware, bundle boundaries, and failure domains.
- **Why rejected**: It does not meet the independent-product premise of the PRD.

### Alternative 2: npm workspace with shared source packages

- **Description**: Use one root lockfile and workspace-linked shared packages.
- **Pros**: Atomic dependency upgrades and fast local development.
- **Cons**: Couples dependency resolution and permits accidental source-level coupling.
- **Why rejected**: The user explicitly selected independently managed npm projects and lockfiles.

### Alternative 3: Separate repositories

- **Description**: Move each frontend into its own source repository.
- **Pros**: Maximum repository and permission isolation.
- **Cons**: Fragments schema coordination, local development, and atomic backend/frontend changes.
- **Why rejected**: Independent delivery is required, but repository separation is not.

## Consequences

### Positive

- Each product has an independent URL, release cadence, runtime, and failure boundary.
- Capture remains small and can optimize specifically for mobile and offline use.
- Admin and Dashboard cannot accidentally expose each other's routes or middleware.
- Exact design-system versions make visual changes explicit and reversible per product.

### Negative

- Three lockfiles and generated clients require three dependency-update workflows.
- Shared fixes may require a design-system release followed by three upgrades.
- Local orchestration and CI must build and verify three applications.

### Risks

- **Version drift**: CI reports outdated design-system consumers and Renovate-style automation opens explicit upgrade changes.
- **Copied business logic**: lint boundaries and reviews prohibit cross-app copies of authorization or domain rules; the API remains authoritative.
- **Inconsistent GraphQL types**: every app generates types from the same canonical schema revision in CI.

## Implementation Notes

- Create all three apps before removing `apps/web`; remove it only after parity tests pass.
- The package publication job produces immutable package versions from tagged commits.
- Deployment health checks and environment variable namespaces are product-specific.
- `scripts/local.sh`, `scripts/verify.sh`, smoke tests, and Docker Compose must address all three services.
