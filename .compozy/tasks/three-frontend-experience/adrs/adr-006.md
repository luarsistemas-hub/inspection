# ADR-006: Use Separate OIDC Clients with Shared SSO and One GraphQL API

## Status

Accepted

## Date

2026-09-07

## Context

Admin and Dashboard need independent sessions and authorization while preserving
identity continuity. Capture must remain accountless and invitation-scoped. The
current API validates one OIDC audience and one CORS origin, and the current
frontend uses Authorization Code with PKCE.

## Decision

Create two public Keycloak clients, `inspection-admin` and
`inspection-dashboard`, with exact redirect URI and web-origin allowlists. Both
use Authorization Code with PKCE and the same Keycloak realm, so an existing
realm session can complete sign-in without asking for credentials again. Tokens
remain in browser memory; neither application stores bearer or refresh tokens in
local storage or JavaScript-readable cookies.

The single GraphQL API accepts an explicit set of trusted audiences and origins.
Verified claims carry the audience into request metadata. Every protected
resolver calls the local authorizer with the required product entitlement,
tenant role, mutation intent, and resource scope. The API reloads membership,
entitlements, and scopes for every protected interaction so revocation is
immediate. Capture continues to exchange invitation link plus OTP for its
short-lived external session and CSRF token; it never accepts OIDC authority.

## Alternatives Considered

### Alternative 1: One OIDC client for both products

- **Description**: Reuse `inspection-web` for Admin and Dashboard.
- **Pros**: Less identity-provider configuration.
- **Cons**: Shared redirect allowlists and audience cannot independently constrain the products.
- **Why rejected**: It weakens product isolation and makes entitlement mistakes harder to detect.

### Alternative 2: Separate backend APIs

- **Description**: Deploy dedicated Admin, Dashboard, and Capture APIs.
- **Pros**: Strong network-level boundaries.
- **Cons**: Duplicates GraphQL composition, domain orchestration, migrations, and operational overhead.
- **Why rejected**: The existing API already owns the shared business model; resolver-level authorization provides the required boundary with less risk.

### Alternative 3: Browser-persisted tokens

- **Description**: Store tokens in local storage for refresh survival.
- **Pros**: Simpler reload behavior.
- **Cons**: Increases token exposure to script compromise.
- **Why rejected**: Silent PKCE reauthentication through the realm session provides continuity without persistent browser tokens.

## Consequences

### Positive

- Compromise or misconfiguration of one client does not authorize the other product.
- SSO continuity remains available without sharing application sessions.
- Revocations and tenant deactivation take effect on the next protected operation.

### Negative

- Keycloak, configuration validation, CORS, security tests, and local setup become multi-value aware.
- A full page reload may require a silent or visible redirect to rebuild in-memory authentication.

### Risks

- **Audience confusion**: the authorizer requires both a trusted audience and matching product entitlement; tests cover cross-product tokens.
- **Open redirects**: each app validates return paths as same-origin relative paths only.
- **CORS broadening**: origins remain exact HTTPS values; wildcards and origin reflection are rejected at startup.

## Implementation Notes

- Replace `INSPECTION_OIDC_AUDIENCE` with parsed `INSPECTION_OIDC_AUDIENCES`.
- Replace `INSPECTION_ALLOWED_ORIGIN` with parsed `INSPECTION_ALLOWED_ORIGINS`.
- Keep capture CSRF and external-session middleware separate from OIDC middleware.
- Configure Admin at local port 3000 and Dashboard at 3002; Capture uses 3003.
