# ADR-008: Publish Reports Through an Audited Visibility Ledger and Customer-Safe Projections

## Status

Accepted

## Date

2026-09-07

## Context

Report snapshots are immutable but currently have no publication state. Internal
report output contains canonical JSON and HTML that must not be exposed directly
to customers. Tenants need manual publication by default or automatic
publication at finalization, customer notifications, simplified and advanced
evidence views, and an audited correction path. Published content must never be
silently erased.

## Decision

Add a versioned tenant `reports.publication_policies` record and a
`reports.report_publications` visibility ledger linked to immutable report
snapshots. Report finalization records the effective policy version. In
`AUTOMATIC` mode it creates the publication in the same transaction as the final
snapshot; in `MANUAL` mode an authorized Dashboard mutation creates it later.
Every final classification, including critical and inconclusive, follows the
same configured mode.

A publication can transition from `PUBLISHED` to `INVALIDATED` or be
`SUPERSEDED`; it is never deleted. Invalidated content stops being the current
customer result, remains as audit metadata, and emits a safe customer notice. A
replacement snapshot becomes visible only through the effective publication
policy. Optimistic versions and `clientMutationId` make publish/invalidate
operations concurrency-safe and idempotent.

Customer GraphQL types are dedicated allowlisted projections and never reuse the
internal `Report` type. Simplified evidence returns approved summaries. Advanced
evidence adds lineage for current, replaced, and discarded items. A sensitive-
blocked item returns safe metadata and `mediaAvailability=SENSITIVE_BLOCKED`,
but never a visual URL, thumbnail, object key, raw HTML, canonical JSON, internal
reasoning, or internal-only finding.

Create per-recipient in-app notification records from the existing transactional
outbox. Dashboard reads them through cursor pagination and periodic refresh;
external email/SMS delivery remains in the existing notification dispatcher.

## Alternatives Considered

### Alternative 1: Add `published` to report snapshots

- **Description**: Mutate each immutable snapshot with a publication flag.
- **Pros**: Small schema change.
- **Cons**: Violates snapshot immutability and cannot represent invalidation, supersession, actor, reason, or policy version cleanly.
- **Why rejected**: Publication is a mutable visibility lifecycle, not report content.

### Alternative 2: Reuse internal report queries for customers

- **Description**: Hide fields in the frontend according to role.
- **Pros**: Minimal API work.
- **Cons**: Sensitive fields still cross the security boundary and can be queried directly.
- **Why rejected**: Customer safety must be enforced by schema and resolver allowlists.

### Alternative 3: GraphQL subscriptions for in-app notifications

- **Description**: Push notifications over WebSockets.
- **Pros**: Lower visible latency.
- **Cons**: Adds connection lifecycle, scaling, proxy, and authorization complexity.
- **Why rejected**: Cursor polling meets current product needs with the existing HTTP stack.

## Consequences

### Positive

- Immutable report content remains reproducible while visibility changes stay auditable.
- Customer APIs cannot accidentally serialize internal report fields.
- Automatic publication has deterministic policy-at-finalization semantics.
- Notification delivery remains at-least-once while recipient records deduplicate user-visible events.

### Negative

- Publication, projection, and notification tables add migrations and consumers.
- Simplified and advanced response mappers require explicit maintenance as report schemas evolve.
- Polling adds bounded repeated reads while Dashboard is open.

### Risks

- **Publication race**: lock or compare policy/report versions in the finalization transaction.
- **Duplicate notifications**: unique `(tenant_id, recipient_membership_id, event_id, kind)` keys make fan-out idempotent.
- **Evidence leakage**: resolver tests assert forbidden fields and absent media URLs for every sensitive state.

## Implementation Notes

- Use the existing outbox to emit `report.published`, `report.invalidated`, and customer progress events.
- Presigned media access remains short-lived and is minted only after authorization and sensitivity checks.
- Customer notification polling uses a 30-second active interval, pauses in hidden tabs, and refreshes immediately on focus.
