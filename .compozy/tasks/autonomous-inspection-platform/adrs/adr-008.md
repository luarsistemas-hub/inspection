# ADR-008: Build a New Inspection Service as Vertical Slices

## Status

Accepted

## Date

2026-09-02

## Context

The repository contains one Contract Service POC with one REST operation. It does not implement inspection behavior, and its request discards photos. Repository guidance requires Vertical Slice Architecture, while the original idea grouped each module into global domain, application, ports, and adapters layers.

## Decision

Create `services/inspection` as a new modular monolith organized by `internal/features/<capability>/<operation>`. Every GraphQL operation, REST operation, RabbitMQ consumer, and scheduled job is an autonomous slice with one exported `Setup` entry point and private DTOs, orchestration, domain rules, and dependency ports. Shared cross-cutting mechanisms live in `internal/platform`; genuinely shared domain types live under the owning capability only after concrete reuse.

Provide `inspection-api`, `inspection-worker`, `inspection-scheduler`, and `inspection-migrate` composition roots from the same Go module. Build one Next.js application for dashboard and capture. Remove `services/contract`, its checked-in binary, and its Swagger artifacts only after the new service passes foundation health and smoke tests.

## Alternatives Considered

### Alternative 1: Extend the Contract Service

- **Description**: Add inspection capabilities beside the existing route.
- **Pros**: Reuses an existing binary and setup.
- **Cons**: Preserves POC naming, incomplete photo behavior, and an unrelated API contract.
- **Why rejected**: The PRD explicitly treats the product as new and the user chose POC removal.

### Alternative 2: Global Layered Modules

- **Description**: Use module-wide domain, application, ports, and adapters directories.
- **Pros**: Matches a conventional Clean Architecture diagram.
- **Cons**: Conflicts with repository VSA guidance and couples unrelated use cases through shared layers.
- **Why rejected**: The existing project requires feature ownership by operation.

## Consequences

### Positive

- Use cases remain independently testable and evolvable.
- API, workers, and scheduler reuse domain code without becoming separate services.
- The obsolete POC cannot mislead developers or users.

### Negative

- Many small Setup functions require explicit composition.
- Cross-slice contracts need disciplined registration and ownership.

### Risks

- Slices may duplicate logic prematurely; extract only demonstrated shared domain behavior.
- A large composition root may grow; group registrations without hiding dependencies in service locators.

## Implementation Notes

Preserve `libs/identity` as the existing generic UUID helper. Do not import `internal` packages from the removed Contract Service.
