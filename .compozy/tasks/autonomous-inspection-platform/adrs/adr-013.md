# ADR-013: Use Transactional Outbox, RabbitMQ, and Idempotent Consumers

## Status

Accepted

## Date

2026-09-02

## Context

Media verification, analysis, reporting, notification, audit projections, and retention are asynchronous and must survive duplicates and process restarts. Publishing directly to RabbitMQ inside a database transaction cannot make the database change and message atomic.

## Decision

Write capability state and a versioned integration-event envelope to a PostgreSQL outbox in one local transaction. Dispatcher workers poll committed rows with `FOR UPDATE SKIP LOCKED`, publish to a durable RabbitMQ topic exchange with publisher confirms, and mark delivery only after confirmation.

Every consumer owns an inbox keyed by event ID and consumer name and acknowledges only after its local transaction commits. The default policy is one initial attempt and three delayed retries at 5 seconds, 30 seconds, and 5 minutes, followed by a DLQ. Each job type applies its documented fallback after DLQ.

## Alternatives Considered

### Alternative 1: Direct Publish During Business Transaction

- **Description**: Publish RabbitMQ messages before or after committing state.
- **Pros**: Less infrastructure code.
- **Cons**: Crashes can lose events or publish changes that never committed.
- **Why rejected**: The product requires reproducible, idempotent asynchronous processing.

### Alternative 2: Change Data Capture

- **Description**: Use Debezium to stream database changes.
- **Pros**: Removes application polling.
- **Cons**: Adds operational infrastructure and exposes storage changes rather than explicit business events.
- **Why rejected**: The user chose transactional polling for the MVP.

## Consequences

### Positive

- Database state and event intent are atomic.
- Duplicate delivery is expected and safely handled.
- Dispatcher and consumers scale horizontally.

### Negative

- Delivery is eventually consistent and requires lag monitoring.
- Every consumer must implement an inbox transaction correctly.

### Risks

- Poison messages can fill retry queues; DLQ alerts and operator-visible replay tooling are required.
- Publishing after a lost confirmation can duplicate delivery; inbox idempotency is mandatory.

## Implementation Notes

The envelope contains `id`, `type`, `version`, `occurredAt`, `tenantId`, `aggregateId`, `correlationId`, `causationId`, and `payload`. Retry topology uses durable queues and TTL dead-letter routing without broker plugins.
