# ADR-016: Render Immutable PDFs Through Gotenberg

## Status

Accepted

## Date

2026-09-02

## Context

Reports require consistent HTML and PDF output with large evidence sets. Embedding a browser in every Go worker increases process complexity, while a native PDF library would duplicate HTML layout behavior.

## Decision

Render report HTML from an immutable report snapshot, then submit it to a private Gotenberg Chromium service. Store the returned PDF as an immutable media artifact associated with that report version. The renderer receives only the already authorized snapshot and short-lived or embedded derivative assets required for that render.

PDF failure follows the standard asynchronous retry schedule. After DLQ, the HTML report remains available internally and an authorized operator can requeue PDF generation without creating a new logical report version.

## Alternatives Considered

### Alternative 1: chromedp Inside the Worker

- **Description**: Start and control Chromium from each report worker.
- **Pros**: No separate rendering endpoint.
- **Cons**: Couples worker health and memory to browser lifecycle.
- **Why rejected**: The user selected an isolated Gotenberg service.

### Alternative 2: Native Go PDF Library

- **Description**: Build PDF pages separately from HTML.
- **Pros**: No Chromium runtime.
- **Cons**: Duplicates layout logic and makes visual parity harder.
- **Why rejected**: One HTML representation should drive both interactive and PDF reports.

## Consequences

### Positive

- Browser crashes are isolated from the Go worker.
- HTML and PDF share one report snapshot and layout source.
- Rendering scales independently.

### Negative

- Local and deployed environments need another private process.
- Asset authorization must work without exposing media publicly.

### Risks

- Renderer requests may leak tenant data if logged; suppress body and signed asset data from logs.
- Dependency or font drift can change output; pin images, fonts, locale, and render settings.

## Implementation Notes

Visual report tests compare rendered pages at stable fixtures and verify that all required text and evidence remain present across page breaks.
