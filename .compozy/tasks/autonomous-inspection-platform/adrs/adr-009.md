# ADR-009: Isolate Tenants with PostgreSQL Row-Level Security

## Status

Accepted

## Date

2026-09-02

## Context

The platform targets up to 100,000 assets and one million historical inspections per tenant. Every interactive, asynchronous, reporting, media, and retention path must prevent cross-tenant access. Schema-per-tenant and database-per-tenant designs add provisioning and migration cost that the MVP does not need.

## Decision

Use one PostgreSQL database with schemas organized by capability. Every tenant-owned table has a non-null `tenant_id`, composite tenant-aware keys and indexes, application authorization checks, and forced PostgreSQL Row-Level Security. Each database transaction sets a transaction-local tenant context before accessing tenant-owned tables. Background messages carry `tenantId`, and workers establish the same context before processing.

Administrative maintenance uses a separate restricted role and explicit code path. Connection-pool reuse must never preserve tenant session state beyond a transaction.

## Alternatives Considered

### Alternative 1: Schema per Tenant

- **Description**: Create a copy of the product schema for every tenant.
- **Pros**: Strong namespace separation.
- **Cons**: Multiplies migrations, connection management, and cross-tenant operations.
- **Why rejected**: Operational overhead is disproportionate for the MVP.

### Alternative 2: Application Filters Only

- **Description**: Depend exclusively on `WHERE tenant_id = ?` conditions.
- **Pros**: Simplest database configuration.
- **Cons**: One missed predicate can expose data.
- **Why rejected**: The user selected RLS plus application checks for defense in depth.

## Consequences

### Positive

- Database policy blocks classes of application authorization mistakes.
- Shared infrastructure remains straightforward to provision and query.
- Capability schemas provide ownership without per-tenant schema multiplication.

### Negative

- Every transaction and test must establish tenant context.
- GORM preload and raw-query behavior require RLS-aware review.

### Risks

- Connection state leakage could cross tenant boundaries; use `SET LOCAL` inside mandatory transaction wrappers and reset tests.
- Owner roles may bypass RLS; runtime roles must not own protected tables and policies must be forced.

## Implementation Notes

RLS isolation tests must cover GraphQL, REST, command/query bus handlers, consumers, scheduler, reports, presigned media, and cleanup jobs.
