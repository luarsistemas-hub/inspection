# ADR-012: Use gqlgen and Browser-Appropriate Session Models

## Status

Accepted

## Date

2026-09-02

## Context

The dashboard and capture PWA share a Next.js application but authenticate differently. Internal users authenticate through OIDC; external users use link and OTP. The user rejected a Next.js BFF for internal GraphQL calls and chose SPA PKCE with in-memory tokens.

## Decision

Use gqlgen schema-first for domain GraphQL. Each GraphQL slice contributes schema and registers its resolver through `Setup`; generated transport types remain at the boundary. Chi serves GraphQL and the limited REST surface for health, readiness, metrics, OIDC support endpoints, and provider webhooks.

Internal dashboard authentication uses OIDC Authorization Code with PKCE. Access tokens remain in browser memory and are sent directly to GraphQL; page reload relies on the IdP session to obtain new tokens and never stores credentials in localStorage. The API resolves OIDC subject to local membership, role, and scope.

External sessions use a two-hour opaque session in a `Secure`, `HttpOnly`, `SameSite` cookie. The server invalidates it immediately when the capture responsibility is finalized, canceled, invalidated, or expired. Recapture requires a new link, OTP, and session.

## Alternatives Considered

### Alternative 1: Next.js Backend for Frontend

- **Description**: Store both internal and external sessions in server-side Next.js cookies and proxy API calls.
- **Pros**: Keeps tokens out of browser JavaScript and centralizes web security.
- **Cons**: Adds a required proxy hop and was rejected by the user.
- **Why rejected**: The user selected direct SPA GraphQL access for internal users.

### Alternative 2: Browser Token Storage

- **Description**: Store access tokens in localStorage or sessionStorage.
- **Pros**: Survives reload without IdP interaction.
- **Cons**: Exposes credentials to browser script compromise.
- **Why rejected**: In-memory internal tokens and HttpOnly external sessions provide safer boundaries.

## Consequences

### Positive

- GraphQL types are generated from one reviewable contract.
- Dashboard tokens are not persisted by application JavaScript.
- External uploads survive refresh without exposing the session token to the PWA.

### Negative

- The dashboard must handle silent reauthentication after reload.
- Direct browser-to-API access requires strict configured origins and CORS behavior.

### Risks

- Cookie-authenticated external mutations are CSRF-sensitive; require same-site deployment, origin checks, and a per-session CSRF token.
- OIDC token claims may become stale; local authorization is evaluated on every request.

## Implementation Notes

GraphQL external-capture operations accept the external cookie and CSRF token, while dashboard operations require an OIDC bearer token. Resolver code never contains business rules.
