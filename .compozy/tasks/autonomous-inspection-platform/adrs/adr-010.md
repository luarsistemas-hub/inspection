# ADR-010: Use GORM with a Dedicated Schema Migrator

## Status

Accepted

## Date

2026-09-02

## Context

The current POC uses GORM and runs `AutoMigrate` during slice setup. The new product requires multiple processes, RLS policies, constraints, outbox/inbox tables, and controlled destructive changes. The user chose to retain GORM and `AutoMigrate` instead of adopting pgx/sqlc.

## Decision

Use GORM for application persistence. Run schema changes only through `cmd/inspection-migrate`; API, worker, and scheduler validate the expected schema version and never call `AutoMigrate`.

`AutoMigrate` handles additive tables, columns, indexes, and compatible constraints. Versioned Go migration steps in the same migrator handle renames, drops, backfills, RLS policies, triggers, and other changes that require explicit ordering or SQL. Each step records an immutable version and checksum and is safe to retry.

## Alternatives Considered

### Alternative 1: pgx and sqlc with SQL Migrations

- **Description**: Generate typed queries from explicit SQL and use SQL migrations exclusively.
- **Pros**: Maximum query and migration predictability.
- **Cons**: Replaces the selected ORM and requires more handwritten data mapping.
- **Why rejected**: The user explicitly chose GORM with AutoMigrate.

### Alternative 2: AutoMigrate in Every Process

- **Description**: Let API, workers, and scheduler migrate during startup.
- **Pros**: Minimal deployment coordination.
- **Cons**: Competing migrations and unpredictable startup behavior.
- **Why rejected**: The user chose a dedicated migrator.

## Consequences

### Positive

- Persistence follows the selected project convention.
- Only one process owns schema evolution.
- Destructive changes remain reviewed, versioned, and testable.

### Negative

- The project maintains both model-driven additive migration and explicit Go migration steps.
- Complex reporting queries may require GORM raw SQL.

### Risks

- AutoMigrate may make an unintended additive change; verify generated schema against contract tests before deployment.
- Model tags alone cannot express all invariants; explicit migrator steps remain mandatory for RLS and advanced constraints.

## Implementation Notes

Slices receive an already migrated `*gorm.DB` or narrower store dependency. They never invoke schema migration from `Setup`.
