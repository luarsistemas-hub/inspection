# ADR-006: Version the template scope and pin an inspection-specific copy

## Status

Accepted

## Date

2026-11-03

## Context

Template schema v2 describes environment capture but has no expected components, detailed views, or handover records. A mutable template cannot serve as the denominator of an inspection already in progress.

## Decision

Add template schema v3 with bounded room/component/view definitions, asset profile default, and supplemental-record definitions. Inspection creation pins the effective scope before invitation; an authorized manager may explicitly revise it only before the first capture activity. Component answers and handover declarations are stored with stable keys, tenant scope, revision, and provenance. Existing v1/v2 templates compile unchanged and receive an empty component scope.

## Alternatives Considered

### Alternative 1: Infer scope from detected items

- **Description**: Reuse catalog output as the expected list.
- **Pros**: No template change.
- **Cons**: Missing items vanish from the denominator.
- **Why rejected**: It violates the product coverage rule.

### Alternative 2: Store only free-form checklist JSON in the report

- **Description**: Keep component answers out of the inspection/capture domain.
- **Pros**: Fewer write paths.
- **Cons**: Cannot support capture guidance, concurrent edits, or reproducible comparison readiness.
- **Why rejected**: The participant needs the scope before the report exists.

## Consequences

### Positive

- Stable coverage, explicit override history, and old-template compatibility.

### Negative

- New template validation and additive storage/migration are required.

### Risks

- Excessive component plans can overwhelm capture; validate bounded template size and use existing media limits.

## Implementation Notes

Resolve the effective scope in the inspection creation transaction and expose a pre-capture revision mutation with optimistic version control. Do not create a cross-service shared abstraction.
