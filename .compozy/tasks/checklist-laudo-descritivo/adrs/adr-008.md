# ADR-008: Build one immutable report snapshot with explicit audience projections

## Status

Accepted

## Date

2026-11-03

## Context

Snapshot v2 carries exception-only inventory; the PDF renderer prints only problems, and the Dashboard hides evidence for a normal classification. Customer projection strips internal findings and needs an explicit descriptive allowlist.

## Decision

Introduce report snapshot v3 containing current-state room/component entries, applied scope and coverage, supplemental records, processing/review status, and complete comparison states. Derive Dashboard/HTML/PDF from that pinned snapshot through separate internal and customer allowlists. Preserve v1/v2 decoders and render historical versions without rewriting them. Regenerate PDF only from the same version and audience projection; later media availability is resolved at access time.

## Alternatives Considered

### Alternative 1: Render live inventory drafts

- **Description**: Query mutable items each time a report opens.
- **Pros**: Less snapshot data.
- **Cons**: Issued reports change after edits and differ across surfaces.
- **Why rejected**: Version stability is a product rule.

### Alternative 2: Add a free-text summary field

- **Description**: Put a new narrative on the existing report.
- **Pros**: Small schema addition.
- **Cons**: Weak provenance and customer projection leakage risk.
- **Why rejected**: Component-level evidence and limits are required.

## Consequences

### Positive

- Consistent facts by audience/version and readable historical artifacts.

### Negative

- More explicit projection and layout code.

### Risks

- Long PDFs can still paginate badly; render short/long fixtures before release.

## Implementation Notes

Keep report-safe IDs, dates, and labels in the snapshot; never embed signed storage URLs, raw media, or private transcript text.
